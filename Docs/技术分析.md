# 《烬灯行者》技术分析

《烬灯行者》是一款 Unity 2D 俯视角生存游戏，核心循环是「移动生存 → 自动攻击 → 清波选卡 → 构筑增强 → 最终胜负」。项目围绕一局游戏组织状态与对象，武器、敌人、构筑和界面共同参与这个循环。

## 整体结构

`EmberGame` 负责创建模块、保存当前阶段、安排每帧调用，并将规则结算结果转换为界面和音效反馈。`EmberCombat` 进一步组织波次、敌人、武器、伤害和死亡处理。

构筑、卡池、生命和 Buff 规则使用普通 C# 类，界面与场景表现通过 Unity 对象实现，生命周期入口由 `MonoBehaviour` 组件提供。这样可以分别处理数值规则与场景表现，规则对象也能直接构造和调用。

模块通过宿主接口或上下文对象获取所需能力。例如，战斗通过 `IEmberCombatHost` 请求玩家受伤、拾取和流程切换；武器通过 `EmberWeaponContext` 查询目标、结算伤害和获取对象池。依赖集中写在这些接口和对象中，具体模块可以围绕有限的输入完成工作。

这些边界目前主要由代码组织和调用约定维护。运行时模块仍位于同一个 `Emberlight.Runtime` 程序集中，尚未通过独立程序集限制模块之间的引用。

## 一、玩家操作与生命

### 统一输入后计算移动

键盘和虚拟摇杆先转换为同一种移动向量，再由 `EmberKeeperMotion.Step` 计算位移。两种输入共用移动速度、Buff 倍率和地图边界，设备差异集中在输入读取部分。

合并输入后只限制向量的最大长度，保留摇杆未推满时的输入强度，同时避免斜向移动或两种输入同时生效时速度叠加。移动完成后再限制地图位置，相机和动画读取实际移动结果，因而能反映边界限制后的角色运动。

移动速度由基础速度与当前 Buff 倍率共同决定。临时效果作用于位移计算，不直接改写基础速度，效果结束时只需更新倍率。

### 生命结算与反馈分开处理

`EmberKeeperVitals` 集中执行「检查阶段与无敌帧 → 应用难度倍率 → 护盾吸收 → 扣除生命」的伤害顺序。接触、暗弹、爆炸和 Boss 技能最终使用同一套玩家承伤规则，难度倍率也在这里统一计算。

规则返回 `Rejected`、`NoChange` 或 `Changed`，`EmberGame` 再决定播放反馈、刷新 HUD 和结束本局。区分「请求被拒绝」与「已结算但生命未变」很有必要：护盾吸收全部伤害时，生命虽然没有减少，本次受伤仍然成立，并会触发无敌帧。

治疗使用相同的结果表示，但保留两个入口。普通 `Heal` 只在未满血时生效，`PickHealingDrop` 允许满血拾取并丢弃溢出治疗。这样，掉落物是否回收不必依赖玩家本次实际增加了多少生命。

## 二、构筑与选卡

### 区分身份定义、本局数据和流程状态

`EmberWeaponCatalog` 保存武器、词条、专属和质变的身份及归属，`RunProgress` 保存本局已经获得的内容。身份定义可以跨局复用，本局数据则在开局时重新建立。

攻击力和攻速按武器分别记录，通用伤害增幅另行保存。这使单武器升级只影响指定武器，也让卡池可以根据已有武器生成对应升级。`EmberWeaponTuning` 提供共享基础参数，`EmberOfferPresentation` 根据同一份构筑和参数生成卡面预览，减少战斗数值与显示数值分别维护造成的偏差。

选卡职责又分为两层：`EmberChoicePool` 负责生成候选，`RunFlowController` 负责何时发卡、还能选几次以及选卡何时结束。候选规则与流程规则各自集中，刷新候选时可以沿用当前选卡流程。

### 生成时去重，提交时验证完整候选

候选生成使用 `(Id, WeaponId)` 作为去重键。同一武器的同一词条只出现一次，品质不同也不会让它变成另一张可重复出现的卡。

提交时则比较完整的 `(Id, Rarity, WeaponId)`。同一词条的效果会受到品质影响，因此提交数据还必须与当前实际展示的品质一致。

随机源从外部传入卡池，规则检查可以使用固定种子。生成候选、刷新和补发都通过已有入口完成，随机数的使用顺序也集中在这些调用中。

### 分开记录计划次数和补偿选卡

`RunProgress.Pending` 表示当前是否还有一次待处理选择，`pendingPicks` 表示本轮剩余的计划内次数，`compensationPick` 表示当前是否正在进行新武器补偿。

这几项状态分别回答不同的问题。刷新只替换当前候选，不增加待选次数；获得新武器时补发一次选择，也不会额外消耗计划次数。

例如，一轮原定选择两次卡牌，第一次选到新武器后，先扣除一次计划次数，再进行一次补偿选卡。补偿结束后，仍剩一次计划内选卡；补偿中获得新武器也不会继续补发。流程结束后，才统一推进下一波。

## 三、武器与伤害

### 用统一入口保留武器差异

六种武器共用 `Tick` 和 `Reset` 入口，各自保存弹体、冷却和形态状态。火球处理飞行与命中，环火处理环绕接触，火雨处理延迟落点；这些差异留在各自实现中。

`EmberWeaponContext` 提供玩家、构筑、敌人查询、伤害和反馈回调。武器可以使用这些能力，具体的扣血、对象创建和音效播放仍由对应模块完成，避免每种武器分别维护一套战斗服务。

`EmberWeaponFactory` 的列表同时确定更新顺序。顺序会影响本帧的伤害、击退和共享燃地，因此它属于实际战斗行为的一部分。

### 区分发射时数据和命中时效果

火球发射时，将基础伤害、永久构筑倍率和形态倍率计算后保存在弹体中；命中时，再读取当前临时 Buff 的伤害倍率。

这种处理明确了不同效果的生效时点。弹体发射后，已经保存的构筑伤害保持不变；临时增伤是否生效，则取决于命中时玩家身上的 Buff 状态。飞行中的火球因此也会受到 Buff 新增或到期的影响。

命中后的敌人扣血、正面减伤、重生和致死回调集中在 `EmberCombatDamage`。各武器只提交目标和伤害来源，铁灯卫减伤、重生等公共规则可以在同一入口执行。

### 共享燃地与频繁对象的复用

火球和环火质变都能留下火区，因此火区由独立的 `EmberBurnGround` 管理。火区的寿命、容量和接触伤害集中维护，玩家未持有燃地武器时，这些火区也能正常生效。

共享燃地仍在 `EmberTrailWeapon` 所在的更新位置结算。火球和环火在本帧较早创建的火区可以参与当帧伤害，保持现有武器顺序下的战斗结果。

`EmberPool` 复用敌人、弹体和掉落视图，`EmberBurnGround` 还复用火区的逻辑记录。专用取池方法先查缓存，缺少对象时才创建，减少命中缓存时的临时委托分配；收集敌人渲染器时复用列表，减少临时数组。

燃地更新还会缓存本帧共用的伤害参数，并先按横纵距离排除明显在范围外的敌人，再进行圆形距离判断。敌人位置仍在每次检查时读取，保留同帧击退对后续命中的影响。

这些优化减少了创建和临时分配，但当前燃地仍逐块遍历敌人，检查次数随火区数与敌人数的乘积增长。对象首次创建和其他初始化也仍有开销。

## 四、敌人与波次

### 将生成节奏、落点和行为分别组织

`EmberWaveDirector` 决定什么时候生成敌人、生成多少，以及何时进入 Boss 预警或清波。`EmberSpawnPlacement` 负责寻找合法落点，`EmberEnemyRoster` 负责创建并登记敌人，行为实现负责具体行动。

这种划分让波次节奏与敌人行动可以分别调整。普通敌人和遭遇敌人的生成位置受到地图与完整相机视口共同约束；找不到合法的屏外落点时，保留配额等待后续生成，避免把一次失败尝试记为已完成生成。

普通敌人通过 `IEnemyBehavior` 区分追击、射击、盾牌和引爆行为。Boss 使用自己的攻击状态处理预警、冲锋、齐射和恢复。它们共用名册、伤害和死亡处理，同时保留不同的行动流程。

### 先完成命中，再统一处理死亡

武器查询敌人时使用名册下标。如果某把武器命中后立即删除目标，后面的敌人下标就会变化，影响同帧仍在运行的其他武器。

当前实现先扣血并标记 `dead`，等全部武器更新后，再由 `ResolveDeaths` 统一处理回调、掉落、计分和回收。分裂子体也先登记请求，随后才加入名册。这样，武器遍历期间的敌人列表结构保持稳定。

致死伤害还可能触发重生或引爆。`OnLethal` 允许行为在真正移除敌人前处理这类情况，死亡奖励则留到最终死亡处理阶段。受击、致死和移除因此具有不同的含义。

烬胎母体目前会在 `SplitBehavior.OnDeath` 和死亡结算分支中分别登记分裂请求，最终子体数量由两处请求共同决定。

### Boss 结束需要单独处理战场状态

普通波需要等待配额完成并清空敌人。Boss 波则从预警开始就带有 Boss 波标记，避免预警期间的空场触发普通清波判断。

Boss 死亡后，还要取消待处理的分裂请求、让伴随兵退场，并移除玩家当前的迟缓效果。退场敌人不补记击杀或掉落，阶段 Boss 随后进入选卡，最终 Boss 进入胜利结算。

这些收尾操作集中在 Boss 结束流程中，使伴随兵和减益状态能够与本次 Boss 战一起结束。

## 五、Buff

### 共享配置，分开保存生效状态

`BuffConfig` 保存不可变的效果规则，`Buff` 保存某个角色身上的生效实例和剩余时间，`BuffManager` 管理实例集合。

多个角色可以共用一份配置，但各自拥有独立的实例与倒计时。增益和减益使用相同的存储与计时方式，由配置中的属性、修正量和减益标记区分。

同 Id 的效果刷新时间，不叠加实例。已有同 Id 的效果生效时，添加请求必须复用它的配置对象；即使数值相同，新建的配置对象也会被拒绝。这样，刷新只影响剩余时间，生效期间使用的规则保持不变。

### 根据当前效果重新汇总属性

移动速度和伤害倍率都从仍在生效的效果重新计算。新增或移除效果后，累加对应属性的修正量，再应用倍率下限。

这样，加速与减速分别到期时，只需重新计算剩余效果。基础速度和武器伤害不会被临时效果反复改写，也就减少了通过乘除或加减恢复属性时产生的误差与顺序问题。

移动模块读取移速倍率，统一伤害入口读取增伤倍率，HUD 读取配置和剩余时间。生效、计算和显示各自使用同一份效果状态。

当前 Buff 规则集中在临时属性修正、同 Id 刷新和到期移除。地面持续伤害由共享燃地处理，敌人的疾风词缀仍由自身的周期逻辑推进。

## 六、界面、画面与声音

### 将界面资源和本局数据分开

`UIRoot` 与 `IntroRoot` 通过 Prefab 保存布局、图片、字号和控件引用。运行时绑定数据与回调、控制显隐，菜单、设置和选卡面板都复用已有控件。

面板复用的同时，业务回调、确认状态和选中动画需要随每次打开、隐藏而更新，避免上一次操作残留。设置面板通过 `SetValueWithoutNotify` 同步滑条，使界面显示当前音量时不会再次触发用户操作回调。

`EmberHudPresenter` 汇集本局与战斗状态，`EmberHud` 更新显示。文字只在对应数据变化时重新赋值，条形控件则按当前数值刷新，减少状态未变时的文字更新。

护盾条按「当前护盾 ÷ 本局累计获得护盾量」填充。护盾耗尽后再次获得护盾时，累计获得量也会继续增加，因此条形可能只恢复到部分填充。归零置灰与重新获得后的配色恢复只改变显示，护盾吸收和叠加仍由 `RunProgress` 结算。

### 将角色动作与移动位置分开

`EmberArtSet` 保存玩家、敌人和庭院模板引用，运行时根据这些引用创建外观。角色、场景资源可以独立编辑，玩法模块继续使用角色位置与状态。

当前玩家使用 Idle、Move 序列帧，`EmberKeeperAnimation` 根据实际位移切换动作和水平朝向。动画表现与角色根节点的移动分开，能够避免视觉摆动改变移动和命中判定使用的位置。

Animator 平时保持 `speed = 0`，由组件在战斗阶段手动推进。角色动画、分件动画和粒子因此可以与暂停、选卡阶段保持一致。

### 集中处理字体、资源和播放反馈

中文字体优先使用预烘焙的 TMP 静态图集，减少运行中补字的需要。`EmberFonts.ValidateBaked` 检查图集、字符与字形关联等资产数据，校验失败时改用动态字体。

静态图集的字形范围在生成时确定，可见文案与字体资源因此存在明确依赖。资产结构校验也无法替代实际排版结果，文字溢出和画面中的可读性仍由具体布局决定。

图集取图服务集中管理资源读取和缓存，切片标识及导入设置保存在 `.meta` 中。例如，`EmberCardFrames` 优先读取持久切片；`EmberUiArt` 先查找旧版具名 Sprite，未找到时再按代码中的归一化区域切图。这些备用区域与整格切片并不完全一致，取图规则会影响实际画面。

`EmberAudio` 分别管理音乐、音效及其音量。战斗和界面提交播放请求，资源加载与实际播放集中在音频模块；音量通过 `PlayerPrefs` 保存，密集音效按非缩放时间限制播放频率。

## 七、单局流程与配置

### 用游戏阶段控制可执行的逻辑

`EmberGame.Phase` 控制加载、菜单、战斗、暂停、选卡和胜负结算。每帧只有在 `Playing` 阶段才推进本局逻辑。

一次调用也可能改变阶段：输入会触发暂停，敌人的攻击可能结束本局。因此，入口在这些调用后再次检查阶段，避免状态已经切换，本帧仍继续处理后续战斗。

角色动画和粒子拥有各自的 Unity 回调，也通过阶段查询决定是否推进。暂停时 `Time.timeScale` 保留玩家选择的倍速，移动、Buff、战斗、角色动画和粒子通过阶段判断停止；界面动画及音效频率控制使用非缩放时间。

这种处理依赖参与本局的更新入口遵守阶段规则。仅暂停 `EmberGame.Update`，无法自动停止其他组件各自的 Unity 回调。

### 分开管理本局世界与常驻界面

`EmberRunState` 保存构筑、配置、生命、Buff 和场景对象引用，`World` 层级承载本局玩家、庭院和战斗视图。开局建立新数据与新世界，结算时保留场景供结果展示，返回营地时再清理。

清理同时涉及两部分：`combat.TearDown` 处理战斗对象和内部状态，销毁 `World` 并调用 `Run.Clear` 则移除本局世界与数据引用。场景 UI 继续保留，下一局沿用同一组控件，并使用新一局的数据与回调。

对象池、分裂请求、Buff 列表和选卡状态都有自己的本局内容，因此销毁世界和清空规则状态需要共同完成，才能避免上一局的数据进入新局。

### 明确配置、构筑和偏好的作用范围

`LevelConfig` 保存本局难度、波次、敌人和地图等配置，`RunProgress` 保存本局获得的武器与升级，`EmberWeaponTuning` 提供武器基础参数和升级增量。配置决定本局采用什么规则，构筑记录玩家在这些规则下获得了什么。

`GameSpeed` 和音量属于跨局保留的玩家偏好，通过 `PlayerPrefs` 持久化。进入战斗时重新应用倍速，确保返回流程重置时间倍率后仍能恢复玩家选择。

地图边界由 `LevelConfig.ApplyWorld` 写入静态字段 `EmberWorld.Limit`，各处位置判定读取同一个值。这符合当前一次运行一个战斗世界的使用方式，也使地图边界具有全局共享的作用范围。
