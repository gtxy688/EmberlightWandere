# 技术分析

本项目是 2D俯视角生存游戏，核心循环是“移动生存 → 自动攻击 → 清波选卡 → 构筑增强 → 最终胜负”。

这里记我们为什么这样写、改动时容易牵连什么。具体调用和工具用法看 [实现说明](实现说明.md)，数值看 [requirements.md](requirements.md)，找模块看 [架构索引](architecture/00-overview.md)。

## 为什么把规则写成普通 C# 类

工程用 Unity 2022.3.62f3、Built-in、正交相机、旧 Input Manager 和 uGUI / TextMeshPro。键盘和摇杆最后合成同一个移动向量，后面的移动逻辑共用。

构筑、抽卡、品质、生命和 Buff 这些规则不需要场景对象，所以用普通 C# 类。改完可以直接测，不必先搭场景。需要显示、资源和生命周期的部分再用 MonoBehaviour；`EmberArtSet` 用 ScriptableObject 保存外观 Prefab。

## EmberGame 负责接线，具体规则放在哪

`EmberGame` 负责创建模块、保存当前阶段、安排调用顺序，以及把结果接到 UI 和音效。

比如玩家受伤：`EmberKeeperVitals` 算难度倍率、护盾吸收和剩余生命，返回 `Rejected / NoChange / Changed`；`EmberGame` 根据结果播声音、刷 HUD，生命归零就结束本局。以后改护盾规则，先看 Vitals 和 `RunProgress.AbsorbDamage`。

选卡也一样：`RunProgress` 改构筑，`EmberChoicePool` 组候选，`RunFlowController` 管选几次、是否补偿和什么时候回到战斗。面板只显示候选、提交点击。

战斗通过 `IEmberCombatHost` 请求受伤、拾取和切换流程；武器通过 `EmberWeaponContext` 取目标、造成伤害、借对象和播放反馈。Combat、Visuals、UI 都不持有 `EmberGame`，这样加功能时不必把入口类传来传去。

## 为什么一帧里要反复检查阶段

暂停、选卡和结算都由 `EmberGame.Phase` 控制。输入可能触发暂停，敌人的一次攻击也可能让玩家死亡，所以这些调用之后会再检查是否还在 Playing，决定本帧能否继续。

角色动画和粒子有自己的 Unity 回调，也要按阶段冻结。UI 动画和音效节流用非缩放时间，调倍速时仍按正常节奏显示和播放。

回营地时清掉本局世界、怪物和构筑，场景里的 UI 保留给下一局复用。

## 刷怪、受击和死亡为什么分开

`EmberWaveDirector` 决定什么时候刷、刷多少；`EmberEnemyRoster` 创建和回收敌人；`IEnemyBehavior` 处理追击、射击、盾卫等行为。调整波次节奏时不需要改每种怪物的行动逻辑。

普通怪和遭遇怪从“相机视口外沿带与地图的交集”取点，`EmberSpawnPlacement` 按合法区域的面积随机采样。没有屏外位置就等下次，不消耗配额。Boss 和分裂子体有单独的落点规则。

武器命中时立即扣血，但回收、计分、掉落和分裂统一留到武器遍历结束后做，避免遍历目标列表时又删除或加入目标。重生先接管死亡，真正死亡才给奖励。母体目前的两路分裂登记暂时保留，数量见需求 §3.7，清理代码时别顺手删一路。

`EmberDrops` 只管地上物品的寿命、吸附和回收。捡药调用生命结算，捡 Buff 请求 BuffManager 添加效果，掉落物自己不改玩家属性。

## Buff 为什么分成三个类

- `BuffConfig` 写效果内容：Id、名字、属性、加成和持续时间。这份配置可以共用。
- `Buff` 是玩家身上实际生效的那一份，保存自己的剩余时间。
- `BuffManager` 管添加、刷新、到期和属性汇总。

Buff 和 Debuff 都是 Buff 对象，用配置区分。目前有增伤、疾行和迟缓；同 Id 刷新时间，不叠层。

移速和伤害从仍生效的 Buff 重新汇总。这样加速与减速先后结束时，不需要“先乘基础值、到期再除回来”，也就不会把别的效果一起还原掉。移动读取移速倍率，伤害在统一入口读取增伤倍率，各武器共用。

Playing 时才扣 Buff 时间，暂停和选卡冻结，普通换波保留，新局和退出清空。HUD 读取剩余时间画图标环，拾取浮字单独用非缩放时间淡出。

## 武器和选卡共用哪些数据

武器 Id、专属与质变归属、名称和基础说明放在 `EmberWeaponCatalog.Definition` 里，避免几张表顺序不同。需要名册数组时用 `RosterCopy()` 拿副本。

基础伤害、冷却、范围和升级增量在 `EmberWeaponTuning`；`EmberWeaponFactory` 创建武器并确定 Tick 顺序。攻击力和攻速按武器分别累计，全体伤害增幅另算一个乘区。

卡片文字与预览由 `EmberOfferPresentation` 根据同一份构筑和参数生成。调数值后同时看实际效果和卡面，别只改显示。

燃地单独交给 `EmberBurnGround`，因为火球和环火质变也会产生火区。即使没拿燃地武器，这些火区也能正常工作。共享火区仍在燃地武器的时隙更新，保留原来的伤害顺序。

火雨是预警结束后的范围伤害，环火是接触伤害，燃地按 dt 持续扣血。燃地目前是地上的区域，离开区域就不再受它影响。

## UI 和美术为什么放进 Prefab

UIRoot 和 IntroRoot 已放在主场景里。布局、图片和控件引用在编辑器里改，运行时绑定数据和回调、控制显隐。菜单、设置、选卡和加载页都复用已有控件；缺引用就报配置错误，方便直接定位资产。

庭院、玩家和敌人模板由 `EmberArtSet` 引用。当前玩家是 Idle / Move 各两帧，怪物和 Boss 按兵种用无脚悬浮皮肤。角色动画改视觉子节点，移动和战斗坐标保持独立。原版、分件和低模小样还留着，方便对比。

中文字体用预烘静态图集，`EmberFonts.ValidateBaked` 检查后再使用，失败回落动态图集。静态图集不能临时补字，所以改可见文案后要查缺字、重烘，并进游戏看实际显示。这几个步骤和保护判断都有用。

## 现在的性能处理和限制

敌人、弹体和掉落复用对象池。专用取池入口先找缓存，缺对象时才创建，命中时不再为了创建工厂生成临时闭包；敌人收集渲染器也复用 List。首次遇到的新对象仍需要创建，敌人的其他初始化也还有分配。

燃地的逻辑对象和视图一起复用，过期或容量满时回收，新局清空旧视图引用。伤害参数每帧查一次，火区位置每块读一次；先按横纵距离排除远处敌人，再做原来的圆形距离判断。敌人位置仍逐次读，保留同帧击退、反向遍历和到期帧的伤害顺序。

粒子有容量限制，设置和升级面板复用控件，HUD 文字只在值变化时更新。燃地目前仍逐个检查敌人，没有加空间索引；想看局部开销可以找 Profiler 的 `Ember.BurnGround.Tick`。分配和固定压力场景在 `EmberCombatPerformanceTests` 检查，整局表现仍结合目标设备看。

Runtime、Editor 和两套测试各有程序集；Runtime 内的模块目前还在同一程序集，目录边界靠代码约定维护。现有规模下用直接调用、少量宿主接口和 context 就够了，暂时没有事件总线或 DI 容器。

Buff 目前只处理临时属性修正、刷新和到期，没有周期伤害或驱散逻辑。敌人的疾风词缀还走自己的周期逻辑。以后确实要做这些功能时，再按实际需求扩展。
