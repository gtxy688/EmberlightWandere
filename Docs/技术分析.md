# 技术分析

本项目用 Unity 实现俯视角生存游戏，核心循环是“移动生存 → 自动攻击 → 清波选卡 → 构筑增强 → 最终胜负”。设计重点是把规则、场景装配和界面反馈分开，使增加武器或调整选卡规则时不必改动整个入口类。

## 规则与装配的边界

`EmberGame` 持有阶段、装配世界与 UI、决定每帧顺序。生命规则属于 `EmberKeeperVitals`，选卡推进属于 `RunFlowController`，构筑与候选分别属于 `RunProgress` 与 `EmberChoicePool`。

生命结算只读取构筑、伤害倍率、阶段三个委托，返回 `Rejected / NoChange / Changed`。它不读取 Transform、Camera，也不创建音频对象。调用方根据结果更新 HUD、播受伤音或收局。选卡宿主只提供构筑、波次奖励、当前阶段与候选，以及显示/收尾回调，不向控制器暴露整局场景状态。

战斗通过 `IEmberCombatHost` 请求扣血、记击杀和结束单局。武器通过 `EmberWeaponContext` 获得选敌、伤害、对象池、燃地和音效反馈能力。UI 通过参数和回调工作。Combat、Visuals、UI 都不持有 `EmberGame` 类型，避免从低层反查入口。

## 构筑与武器

`EmberWeaponCatalog.Definition` 将武器 ID、专属 ID、质变 ID、名称和基础说明放在同一条记录里。开局选择、升级说明、归属判断都读这一张表；数组兼容入口返回副本，外部修改不会破坏名册。

`EmberWeaponTuning` 集中基础伤害、冷却、速度、范围和升级增量；`EmberWeaponFactory` 维护实现注册与顺序。攻击力和攻速加成仍作用于指定武器，全体伤害增幅使用独立乘区。品质表与需求数值仍由既有 M2 配置负责。

共享燃地由 `EmberBurnGround` 管理，燃地武器只负责产生脚下火焰与火海圈；火球、环火质变也能投递燃地。战斗在原燃地武器时隙推进共享效果，保证本帧生成的火焰仍在原顺序结算，不因未拥有燃地武器而失效。

## 界面、资源与可读性

`EmberOfferPresentation` 生成标题、说明、数值预览和徽章；`EmberUpgradePanel` 绑定缓存控件、按钮与动画。EmberUiFactory 和旧快照补建在 Editor 程序集，运行时已移除动态创建回退；缺少引用或控件容量不足时报配置错误。

主场景保存 UIRoot 与 IntroRoot Prefab 实例，`EmberUiRoot`、`EmberIntroView` 只持有序列化视图引用；`EmberMenuUi.Bind` 和 EmberIntro 在字体校验后使用已有视图。布局与静态图片在编辑器中调整，运行时负责数据、状态、回调、加载进度和按候选数量排卡。菜单、开局选择、设置与升级复用控件，加载结束只隐藏 IntroRoot。Editor 连接工具负责旧快照迁移与首次生成加载页，不进入 Runtime 程序集。

设置和升级控件复用，战斗弹体与效果使用对象池，粒子有容量上限。这里描述的是实现手段，**没有据此声称达到某个 FPS 或 GC 指标**。源码使用一致的缩进和展开代码块；中文文件以 UTF-8 保存。排版重整经过语法 token 对比，避免改变代码含义。

中文字体优先加载预烘静态图集，经过 `EmberFonts.ValidateBaked` 才投入运行；失败回落动态图集。修改文案须重烘、检查编译后程序集的字符串覆盖，并验证实际 TMP 网格与画面。

## 取舍与边界

当前工程按 Runtime、Editor、EditMode.Tests、PlayMode.Tests 划分程序集，Runtime 内各模块仍在同一程序集，目录边界不是编译器强制隔离。没有为每个类增加接口，也没有引入全局事件总线、DI 容器或通用状态效果框架。

普通与遭遇杂兵按相机完整视口外沿带和地图交集取随机点，无法生成时不消耗配额；Boss/分裂保留特殊位置。HUD 缓存显示值，变化时才格式化文字，波次文字只有一个写入点。具体调用链和编辑器工具用法见 [实现说明](实现说明.md)，工程运行与交付方式见 [README](../README.md)。
