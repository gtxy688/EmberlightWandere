# 技术分析

本项目用 Unity 实现俯视角生存游戏，核心循环是“移动生存 → 自动攻击 → 清波选卡 → 构筑增强 → 最终胜负”。设计重点是把规则、场景装配和界面反馈分开，使增加武器或调整选卡规则时不必改动整个入口类。

本文说明当前实现的设计原因与取舍；实际调用链、运行和交付方式见 [实现说明](实现说明.md)。玩法及可调参数统一见 [需求文档](requirements.md)，模块边界与维护入口见 [架构总览](architecture/00-overview.md)。

## 技术选择

工程使用 Unity 2022.3.62f3、Built-in 渲染管线、正交相机、旧 Input Manager 与 uGUI / TextMeshPro。键盘与虚拟摇杆最终产生同一种移动向量，战斗规则无需区分输入设备。

核心规则采用普通 C# 类，由场景入口显式创建和驱动；需要显示、资源或场景生命周期的部分才使用 Unity 组件。这样既保留 Unity 编辑资源的便利，也能让构筑、品质和生命结算脱离场景测试。玩法参数由静态配置类维护，适合原型中的集中修改；美术集使用 ScriptableObject 保存 Prefab 引用，不把玩法规则放进外观资产。

## 规则与装配的边界

`EmberGame` 持有阶段、装配世界与 UI、决定每帧顺序。生命规则属于 `EmberKeeperVitals`，选卡推进属于 `RunFlowController`，构筑与候选分别属于 `RunProgress` 与 `EmberChoicePool`。

生命结算只读取构筑、伤害倍率、阶段三个委托，返回 `Rejected / NoChange / Changed`。它不读取 Transform、Camera，也不创建音频对象。调用方根据结果更新 HUD、播受伤音或收局。选卡宿主只提供构筑、波次奖励、当前阶段与候选，以及显示/收尾回调，不向控制器暴露整局场景状态。

战斗通过 `IEmberCombatHost` 请求扣血、记击杀和结束单局。武器通过 `EmberWeaponContext` 获得选敌、伤害、对象池、燃地和音效反馈能力。UI 通过参数和回调工作。Combat、Visuals、UI 都不持有 `EmberGame` 类型，避免从低层反查入口。

阶段由组合根统一持有。暂停、升级和结算时停止推进战斗；输入或受伤可能在帧内切换阶段，因此调用后重新检查阶段，避免玩家死亡后仍继续攻击或发牌。返回营地回收本局世界与战斗状态，场景 UI 保留供下局复用。

## 敌人、死亡与掉落

`EmberWaveDirector` 管波次配额和出场时机，`EmberEnemyRoster` 管敌人实例，`IEnemyBehavior` 管追击、射击、盾卫等行为。行为通过 context 请求移动或攻击，伤害与最终死亡由 `EmberCombatDamage` 统一处理，避免每种武器各自记分和生成掉落。

普通与遭遇杂兵的生成区域是“相机视口外沿带”与地图的交集。`EmberSpawnPlacement` 把合法区域拆成矩形，按面积随机取点；无合法区域则返回失败，不在屏内兜底，也不扣除生成配额。Boss 与分裂子体保留各自的特殊落点。

死亡在本帧武器遍历结束后集中结算，避免遍历目标时删除列表元素。重生词缀先接管死亡，最终死亡才生成掉落、回收敌人并计分；分裂落点先暂存，再由战斗根生成子体。`EmberDrops` 管理治疗和 Buff 掉落的吸附、拾取、寿命与回池，分别经宿主进入生命结算或 Buff 管理器，不直接修改玩家属性。

## Buff 对象与临时效果

`BuffConfig` 保存不可变的效果规则，`Buff` 保存某个使用者当前剩余的持续时间，`BuffManager` 管理添加、刷新、到期与属性汇总。定义可以共享，倒计时分别维护；增益和 Debuff 使用同一套对象，配置标记效果类型。

玩家拾取物品可获得临时增伤、疾行；暗烛射手的青色技能弹命中后可施加迟缓。掉落和技能只报告施加请求，不管理倒计时。移动读取汇总后的移速倍率，所有武器在统一伤害入口读取临时增伤，避免每把武器重复接线。

临时效果独立于选卡构筑。到期时移除其贡献并重新汇总，不采用先改基础值、到期再除回去的做法，因此加速与减速交错结束不会破坏其他效果。Playing 阶段计时，暂停和选卡冻结，普通换波保留，退出与新局清空；HUD 从只读列表更新图标计时环与秒数，并把新增 / 刷新结果转成角色浮字。浮字使用有限缓存和真实时间上移淡出，既不改效果计时，也不在运行时建立 UI 控件。

## 构筑与武器

`EmberWeaponCatalog.Definition` 将武器 ID、专属 ID、质变 ID、名称和基础说明放在同一条记录里。开局选择、升级说明、归属判断都读这一张表；数组兼容入口返回副本，外部修改不会破坏名册。

`EmberWeaponTuning` 集中基础伤害、冷却、速度、范围和升级增量；`EmberWeaponFactory` 维护实现注册与顺序。攻击力和攻速加成仍作用于指定武器，全体伤害增幅使用独立乘区。品质表与需求数值仍由既有 M2 配置负责。

共享燃地由 `EmberBurnGround` 管理，燃地武器只负责产生脚下火焰与火海圈；火球、环火质变也能投递燃地。战斗在原燃地武器时隙推进共享效果，保证本帧生成的火焰仍在原顺序结算，不因未拥有燃地武器而失效。

AOE 通过区域内目标判定实现：火雨在预警结束后结算范围伤害，环火按接触判定，共享燃地按帧积分持续伤害。当前燃地是世界中的伤害区域，并不是附着到敌人身上、离开区域后仍持续的灼烧状态。

## 界面、资源与可读性

`EmberOfferPresentation` 生成标题、说明、数值预览和徽章；`EmberUpgradePanel` 绑定缓存控件、按钮与动画。EmberUiFactory 和旧快照补建在 Editor 程序集，运行时已移除动态创建回退；缺少引用或控件容量不足时报配置错误。

主场景保存 UIRoot 与 IntroRoot Prefab 实例，`EmberUiRoot`、`EmberIntroView` 只持有序列化视图引用；`EmberMenuUi.Bind` 和 EmberIntro 在字体校验后使用已有视图。布局与静态图片在编辑器中调整，运行时负责数据、状态、回调、加载进度和按候选数量排卡。菜单、开局选择、设置与升级复用控件，加载结束只隐藏 IntroRoot。Editor 连接工具负责旧快照迁移与首次生成加载页，不进入 Runtime 程序集。

手绘样板把玩家、普通敌人和庭院资源从组合根中移出，由 `EmberArtSet` 引用 Prefab。运行时仍创建本局实例，但外观、比例和环境位置可在编辑器调整；角色动画只改变外观子节点。战斗栏使用九宫格图片，数值、血条和交互保持独立控件。当前仅接入小规模样板，其他兵种、边界和菜单尚沿用原外观，因此不宣称整套美术已统一。

设置和升级控件复用，敌人、弹体和掉落视图使用对象池，粒子有容量上限。HUD 缓存显示值，变化时才格式化文字，波次文字只有一个写入点。这些措施减少重复创建和无效 UI 更新，但池未命中时仍会分配，区域伤害也仍需遍历目标；**不能据此声称零 GC 或达到某个 FPS 指标**，性能结论需要在目标设备测量。

中文字体优先加载预烘静态图集，经过 `EmberFonts.ValidateBaked` 才投入运行；失败回落动态图集。修改文案须重烘、检查编译后程序集的字符串覆盖，并验证实际 TMP 网格与画面。

## 取舍与边界

当前工程按 Runtime、Editor、EditMode.Tests、PlayMode.Tests 划分程序集，Runtime 内各模块仍在同一程序集，目录边界不是编译器强制隔离。没有为每个类增加接口，也没有引入全局事件总线或 DI 容器。Buff 系统当前聚焦临时属性修正和刷新到期，不预建周期伤害、驱散等尚无使用方的机制。

单武器强化、全体伤害增幅与护盾属于构筑增益；即时治疗、临时 Buff 和区域伤害分别由对应模块负责。原有敌人疾风词缀仍按其周期规则推进，不为了复用而改变既有敌人行为。

工程交付保留完整源码、场景、Prefab、实际资源及 `.meta`、包清单和项目设置，使接收者能重新导入和修改。缓存 Library 不属于交付前提；运行与导出入口见 [README](../README.md)。
