# 笔试题 2 符合性核查

> 题目：**第 2 套｜2D 俯视角生存原型**——WASD/摇杆移动 + 摄像机跟随；丧尸从屏幕外随机生成并追踪玩家；玩家自动攻击；敌人死亡掉落物品。进阶：buff / debuff / aoe，以及可扩展性与可维护性。文档：要求有基本的技术分析、实现文档。
>
> 核查日期：2026-10-14。代码基线：本轮注释精简与文档重构之后的工作区。Unity 2022.3.62f3。
> 本文件是**核查结论与证据记录**。产品行为与数值的权威仍是 [`requirements.md`](requirements.md)，模块边界见 [`architecture/00-overview.md`](architecture/00-overview.md)。

## 结论

**基础四项要求全部有源码实现，进阶项部分达成，工程与文档齐备；可以直接作为这道题的提交基础。**

| 题目要求 | 判定 | 一句话依据 |
|----------|------|------------|
| 2D 俯视角 | **符合** | 正交相机 + XY 平面移动；Built-in 管线 |
| WASD / 摇杆移动 | **符合** | `EmberInput` 读 `Horizontal`/`Vertical`，并自绘触屏摇杆 |
| 摄像机跟随 | **符合** | `EmberKeeperMotion.Follow` 把相机贴到灯芯 XY，Z 固定 −10 |
| 丧尸从屏幕外随机生成 | **符合** | `EmberSpawnPlacement` 按完整视口 + 外沿带 + 地图交集取点，无合法区域时延后且不消耗配额 |
| 追踪玩家 | **符合** | `ChaseBehavior.Tick` 朝玩家推进，四类特殊行为均继承它 |
| 玩家自动攻击 | **符合** | 六把武器各自 `Tick` 自动开火，无需攻击键 |
| 敌人死亡掉落物品 | **符合** | `EmberHealingDrops` 概率掉落回血道具，可拾取 |
| 进阶：buff | **符合** | 单武器攻击力/攻速、全局增幅、护盾、敌人词缀强化 |
| 进阶：debuff | **不完整** | 只有区域持续伤害（燃地/火海/灼热/暗焰），**没有附着在目标上的限时状态** |
| 进阶：aoe | **符合** | 环火、燃地、天降火雨、爆炸、暗弹落点 |
| 可扩展性 / 可维护性 | **符合，且是本项目的强项** | 组合根 + 模块契约 + 四程序集 + EditMode 套件 |
| 技术分析与实现文档 | **符合** | [`技术分析`](技术分析.md) + [`实现说明`](实现说明.md) + 模块架构/验收文档 |

需要留意的两点风险，都不是功能缺失：

1. **debuff 是唯一实质性空白**。题面把 buff / debuff / aoe 并列为进阶举例，前两项与 aoe 都有实现，debuff 只能算「区域持续伤害」的近似。本项目已有现成的扩展点（`IEnemyBehavior` 的 `Tick(dt, ctx)` 每帧都能拿到敌人），补一个限时减速或易伤状态的成本很低，收益是让进阶项从「部分」变成「齐备」。
2. **敌人主题是"烬影/披风怪"，不是"丧尸"**。基础敌人由 `Cloak / Hood / Face / Eye` 组合成 `Shade`，配色偏暗紫。题面写的是「丧尸」，本项目是自成一套的熄灯主题。这是**主题替换，不是功能缺失**——是否接受需要提交方自己判断；若希望降低歧义，把默认追击怪的外观与命名做成更直白的丧尸形象即可，其余特殊怪仍可保留为扩展。

## 逐项核查

### 1. 2D 俯视角

`EmberGame.Start` 把主相机设为正交（`orthographicSize = 8`），玩家与敌人都只在 XY 平面移动，Z 只用于相机景深。

- 相机配置：`Assets/Scripts/Core/EmberGame.cs:101-102`（`cam.orthographic`）（`orthographic`、`orthographicSize`、纯色背景）
- 玩家位移：`Assets/Scripts/Core/EmberKeeperMotion.cs:17`（`Step`）
- 世界边界：`Assets/Scripts/Combat/EmberWorld.cs`

### 2. WASD / 摇杆移动 + 摄像机跟随

键盘走旧版 Input Manager 的 `Horizontal` / `Vertical`（默认映射含 WASD 与方向键）；触屏与鼠标拖拽在下半屏生成虚拟摇杆。两路输入相加后统一钳到单位长度，因此斜向不会更快。

- 键盘轴：`Assets/Scripts/Core/EmberInput.cs:92`（`KeyboardAxis`）
- 摇杆解析与触发区：`Assets/Scripts/Core/EmberInput.cs:50`（`Tick`）（下半屏 `MoveZoneHeightRatio = .7`）
- 合并与限幅：`Assets/Scripts/Core/EmberKeeperMotion.cs:21`（`ClampMagnitude`）
- 相机跟随：`Assets/Scripts/Core/EmberKeeperMotion.cs:29`（`Follow`）
- 按键映射：`ProjectSettings/InputManager.asset`

### 3. 敌人从屏幕外随机生成并追踪玩家

**落点规则**（`requirements.md` §3.1）：普通与遭遇杂兵在「完整相机视口外 + 屏外预留边距 1.2 + 外沿带宽 2 + 地图内缩 0.8」的合法区域内随机取点；取不到合法位置时**本次不刷**、不消耗配额，下一帧重试。这保证不会出现"钳制回屏内"的兜底。

- 取点算法：`Assets/Scripts/Combat/EmberSpawnPlacement.cs:8`（`TryFind`）（视口矩形与外沿带）
- 矩形分区取样：`Assets/Scripts/Combat/EmberSpawnPlacement.cs:38`（`TryFind`）（四块区域按面积加权 + 结果复核）
- 刷怪入口：`Assets/Scripts/Combat/EmberEnemyRoster.cs:54`（`Spawn`）
- 配额只在成功时消耗：`Assets/Scripts/Combat/EmberWaveDirector.cs:169`（`TrySpawnRolledTrash`）
- 敌人上限 150：`Assets/Scripts/Core/LevelConfig.cs:24`（`EnemyLimit`）

**两处有意例外**（`requirements.md` §3.1 末段已写明）：Boss 在玩家上方 2 单位出场；烬胎母体死亡后在其落点周围补生成子体（`allowInView: true`）。这两条属于派生/特殊出场，不适用屏外规则。

**追踪**：`ChaseBehavior.Tick` 向 `ctx.Delta`（玩家 − 自身）方向推进；射手、盾卫、烬胎、引线虫都继承它，只在开火/朝向/引爆上有差异。

- 追踪：`Assets/Scripts/Combat/Enemies/EmberEnemyBehavior.cs:43`（`Tick`）
- 行为分派：`Assets/Scripts/Combat/EmberEnemyRoster.cs:140`（`CreateBehavior`）

### 4. 玩家自动攻击

每帧 `EmberCombat.TickWeapons` 驱动全部武器实例；武器自己查最近/随机可见目标，无需玩家按键。六把武器各自的自动行为：

| 武器 | 自动行为 |
|------|----------|
| 火球 | 自动锁定最近可见敌人并发射 |
| 环火 | 绕玩家旋转，接触即结算持续伤害 |
| 燃地 | 沿移动路径留下火焰，踩踏掉血 |
| 穿透火矢 | **基本静止时**开火，一箭穿多（需求明确的专属手感） |
| 回旋烬蝶 | 掷出后去程/回程都能命中 |
| 天降火雨 | 自动标记目标区域，预警圈后范围伤害 |

- 每帧推进：`Assets/Scripts/Combat/EmberCombat.cs:257`（`TickWeapons`）
- 自动选敌：`Assets/Scripts/Combat/Weapons/EmberWeapon.cs`（`FindNearestVisibleEnemy` / `FindRandomVisibleEnemy`）
- 未拥有武器的自门控：各武器 `Tick` 开头的 `ctx.Progress.OwnsWeapon(...)` 判定

### 5. 敌人死亡掉落物品

死亡结算里调用治疗掉落，生成可见拾取物，随后由吸附、拾取与生命结算消费。这是**概率掉落**，题面没有要求"每次必掉"：

| 死亡者 | 掉落概率 |
|--------|----------|
| 普通敌人 | 8%（`HealDropChance`） |
| 带词缀敌人 | 20%（`EliteHealDropChance`） |
| Boss | 100% |
| 分裂子体（引线虫 kind 6） | 不掉 |

- 概率判定：`Assets/Scripts/Combat/EmberHealingDrops.cs:16`（`ShouldDrop`）
- 死亡时调用：`Assets/Scripts/Combat/EmberCombatDamage.cs:136`（`HealingDrops.OnDeath`）
- 吸附与拾取：`Assets/Scripts/Combat/EmberHealingDrops.cs:31`（`Tick`）
- 拾取结算（任意血量可拾取、溢出丢弃）：`Assets/Scripts/Core/EmberKeeperVitals.cs:137`（`PickHealingDrop`）

> `requirements.md` §5 的「死亡掉落已删除」**专指余烬计分拾取物**被删（击杀直接记 Score），不代表所有死亡掉落都被删除。治疗掉落仍在，且是题面这一条的实现。

### 6. 进阶：buff / debuff / aoe

**buff 有实现**：

- 单武器攻击力 / 攻速（只作用于对应已有武器，不是全局）
- 全体伤害增幅（全局独立乘区）
- 护盾（可叠加，受伤优先消耗）
- 敌方词缀强化：灼热、疾风、重生

**aoe 有实现**：环火接触、燃地/火海持续区域、天降火雨落点、引线虫爆炸、Boss 暗焰落点。

**debuff 是空白**：全仓没有附着在单个敌人身上、带持续时间的状态（减速 / 易伤 / 定身 / 灼烧）。现有的"灼热"和"燃地"都是**区域伤害**，敌人离开区域就结束，不构成 debuff。

- 区域伤害：`Assets/Scripts/Combat/EmberBurnGround.cs`、`Assets/Scripts/Combat/EmberCombat.cs:312`（`inBurningAura`）（灼热光环脉冲）
- 敌人词缀：`Assets/Scripts/Core/LevelConfig.cs:39`（`WindPeriod`）、`Assets/Scripts/Combat/EmberCombat.cs:389`（`SetEnemyContext`）（疾风倍速）
- 行为接口（现成的 debuff 扩展点）：`Assets/Scripts/Combat/Enemies/EmberEnemyBehavior.cs:7`（`IEnemyBehavior`）

### 7. 可扩展性与可维护性

这一项是本项目投入最多的地方，也是相对同类笔试作业最容易看出差距的地方：

- **组合根只管装配与顺序**：`EmberGame` 明确不承载业务规则；伤害结算、选卡推进、构筑、波次各自独立成类。
- **契约解耦**：战斗经 `IEmberCombatHost` 与宿主通信；武器经 `EmberWeaponContext` 取能力；表现层注入阶段委托而不是反查游戏实例。`Assets/Scripts/Combat/`、`Visuals/`、`UI/` 三处零 `EmberGame` 类型引用。
- **纯逻辑可脱离 Unity 单测**：`RunProgress`、`EmberChoicePool`、`EmberWeaponCatalog`、`EmberRarityUtil` 零 `UnityEngine` 引用。
- **四程序集**：`Emberlight.Runtime` / `Emberlight.Editor` / `Emberlight.EditMode.Tests` / `Emberlight.PlayMode.Tests`。
- **数值集中**：可调数值在 `LevelConfig` 与 `EmberWeaponTuning`，不在战斗逻辑里散落魔法数。
- **扩展路径有文档**：新增武器 / 调整卡池 / 修改卡面 / 新增 buff-debuff 的落点写在 [`实现说明.md`](实现说明.md) 的「扩展位置」。

## 需要改进的点（按性价比排序）

1. **补一个可观察的 debuff**（唯一实质缺口）。建议做一个最小的、规则说清楚的示例：武器命中施加限时减速，明确持续时间、重复命中刷新还是叠加、到期恢复、敌人死亡或回池时清理。落点可以是 `EmberEnemy` 上的一个状态字段 + `EmberCombat.TickEnemies` 里的推进，或 `IEnemyBehavior` 的装饰实现。改完记得重烘字体并跑 EditMode。
2. **确认「丧尸」主题**。当前默认追击怪是暗影披风造型（`Shade`）。如果阅卷人会严格对照题面，建议至少让默认追击怪具备更直白的丧尸外观与命名。
3. **交付前重跑一次完整验证**：离线编译 → EditMode → 图形 PlayMode → 字形覆盖，并重新导出工程包（现有 `Delivery/` 内的包早于本轮改动）。
4. **人工试玩一遍主闭环**：菜单 → 四步开局 → 移动 → 自动攻击 → 掉落拾取 → 清波选卡 → 暂停 → 胜/负结算。手感与观感无法由自动化替代。

### 待人工验收

- 实际 WASD / 摇杆响应与相机表现。
- 完整闭环：菜单 → 四步开局 → 移动 → 自动攻击 → 掉落拾取 → 清波选卡 → 暂停 → 胜/负结算 → 再开一局。

### 未验证

- Android 构建与真机表现、CPU/GC 性能量化。
- 无缓存新目录下的首次导入（`Delivery/` 内现有包早于本轮改动，提交前必须重新导出）。
- 自动化对 M1 配置、M3 波次/Boss 边界、M4 六武器行为、M5 敌人行为、M8 音频接线的覆盖——各模块验收文档中仍标「待建」。

> 静态源码核查与自动化测试都**不能**代替手感与审美验收；反之，手感良好也不能代替边界规则的正确性。
