## 结论

**现有项目适合作为这道笔试的基础，主要玩法已经具备，但当前版本不宜直接宣称「完全符合且可直接交付」。**

基础功能中，WASD / 虚拟摇杆、相机跟随、自动攻击、敌人追击、死亡治疗掉落均有明确实现。主要硬缺口是「从屏幕外随机生成」没有得到保证。进阶方面，属性强化、护盾、敌人词缀和 AOE 已有实现；独立的 debuff 示例不够明确。交付方面，当前缺少面向阅卷人的运行入口说明，权威文档仍有互相冲突的旧描述，首次导入又包含一个与玩法无关的 Git 开发插件依赖。

**目前更有价值的工作是补齐题面与交付缺口、提高源码可读性，然后做干净工程验收。继续扩大武器、Boss 或局外系统的收益较低。**

### 1. 2D 俯视角生存原型：源码与配置基本符合

- `EmberGame.Start` 将相机设为正交；玩家与敌人在 XY 平面移动。
- 已有生命、接触伤害、自动武器、波次和胜负流程。
- 当前是清波选卡、阶段 Boss 的生存玩法。题面没有要求必须无限刷怪，也没有要求 XP，因此这些差异不能直接算不符合。
- 场景中 `Emberlight Game` 挂载 `EmberGame`，GUID 与脚本 `.meta` 对得上；唯一启用场景是 `Emberlight.unity`。

### 3. 丧尸从屏幕外随机生成并追踪玩家：追击符合，生成位置存在明确缺口

`ChaseBehavior.Tick` 向玩家方向移动，普通敌人的追击链成立。但生成位置不是按相机视口计算：

- 常规敌人：玩家周围半径 10 的随机圆环，再进行地图边界 Clamp。
- 遭遇敌人：玩家周围半径 5 的圆环，可直接位于屏内。
- Boss：玩家上方 2 个单位，属于明确的屏内生成设计。
- 分裂子体：在母体死亡点附近生成，属于派生生成，通常应与常规刷怪分开定义验收。

可计算的反例：相机正交半高为 8，采用 540×960 竖屏时半宽为 4.5。玩家在 `(22, 0)`，常规刷怪朝右取 `(32, 0)`，Clamp 后为 `(21.2, 0)`。其视口坐标约为 `(0.4111, 0.5)`，在屏内，甚至满足当前武器的可见目标范围。遭遇在玩家原点正上方 5 个单位时，视口坐标约为 `(0.5, 0.8125)`，也在屏内。

这属于**源码算法及几何计算确认的缺口**，不是已在 Play Mode 复现的画面观察。

另外，当前敌人的基础外观由 `Cloak / Hood / Face / Eye` 组合形成，命名为 `Shade`，更接近烬影或披风怪。是否允许这种主题替换，题面没有说明；不能把「怪物追击」直接当成「丧尸主题」也完全满足。若希望降低评分歧义，建议至少让默认追击怪具备明确的丧尸外形和命名，保留其他特殊怪作为扩展。

证据：[常规刷怪](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/EmberEnemyRoster.cs:59)、[遭遇落点](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/EmberWaveDirector.cs:227)、[追击](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/Enemies/EmberEnemyBehavior.cs:41)、[基础外观](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Visuals/EmberVisuals.cs:38)。

### 4. 玩家自动攻击：实现符合

`EmberGame.Update → EmberCombat.Tick → TickWeapons → EmberWeapon.Tick` 自动推进武器，无需攻击键。火球按冷却寻找最近可见目标，环火自动环绕并结算接触伤害，陨石自动选取可见目标。

个别武器有行为条件，例如穿透火矢需要基本静止；这是已在需求中明确的专属规则，不代表整体自动攻击缺失。

证据：[每帧武器推进](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/EmberCombat.cs:291)、[火球自动开火](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/Weapons/EmberBasicShotWeapon.cs:25)。

### 5. 敌人死亡掉落物品：已有治疗掉落，实现符合

死亡结算会调用 `EmberHealingDrops.OnDeath`，生成可见治疗物，随后通过吸附、拾取和生命结算消费。

这是概率掉落；普通敌人不保证每只都掉，Boss 保证掉，分裂子体不掉。截图未规定每次死亡必掉，因此不应把概率机制判为缺失。为了让阅卷人容易验证，应在说明里写清掉落触发条件与可观察路径。

`requirements.md` §5 的「死亡掉落已删除」具体指余烬计分拾取物被删除，**不能据此推断所有死亡物品掉落都被删除**；§4.4 与源码仍保留治疗掉落。

证据：[死亡调用](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/EmberCombatDamage.cs:133)、[掉落与拾取](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/EmberHealingDrops.cs:16)。

### 6. buff / debuff / AOE：已有部分覆盖，debuff 示例建议补齐

- **buff / 强化**：单武器攻击力与攻速强化、全体伤害增幅、护盾；敌人也有疾风、重生等强化词缀。
- **AOE**：环火、燃地、陨石等可以影响范围内多个敌人。陨石通过半径遍历进行范围结算。
- **debuff**：当前燃地是区域持续伤害；火球质变命中后生成燃地，没有看到独立附着在目标上的减速、易伤、带持续时间的灼烧状态。敌方灼热光环也属于区域伤害，不能直接当作已有通用 debuff 系统。

题面将这些列为进阶举例，没有提供逐项扣分规则。这里应描述为「进阶展示不完整」，而不是认定全部进阶功能不存在。

建议补一个小而完整的示例，例如武器命中施加短时减速，定义持续时间、重复命中刷新/叠加规则、到期恢复和死亡/回池清理。用配置和一个清晰的效果入口展示扩展能力，无需为笔试搭建复杂的通用技能框架。

证据：[属性强化](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Core/RunProgress.cs:279)、[陨石 AOE](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/Weapons/EmberMeteorWeapon.cs:54)、[火球命中生成燃地](E:/Unity/Projects/DemoProjects/EmberlightWandere/Assets/Scripts/Combat/Weapons/EmberBasicShotWeapon.cs:65)。

### 7. 可扩展性与可维护性：已有良好基础，还有源码表达方面的改进空间

已存在的优势：

- `EmberGame` 与 `EmberCombat` 负责装配和推进顺序，波次、敌人名册、伤害、掉落已分开。
- 武器使用 `EmberWeapon` 与 `EmberWeaponContext`，敌人行为使用 `IEnemyBehavior`。
- 战斗宿主通过 `IEmberCombatHost` 注入；本轮文本扫描中的 `EmberGame` 命中均为注释说明，没有发现 Combat / Visuals / UI 中的实际类型依赖。
- `RunProgress` 是不引用 UnityEngine 的构筑逻辑，有真实 EditMode 测试。
- Runtime、Editor、Tests 三个程序集区分明确。注意它们**没有**把每个 Runtime 业务模块单独隔离，不能宣传为编译器已经禁止所有模块间违规引用。
- 敌人、弹体、掉落和部分特效使用对象池；这能说明复用设计，不能直接证明零 GC 或某设备上的帧率。

值得改进：

- 武器行为常量仍散在各个脚本内，例如火球冷却、基础伤害、速度与寿命，陨石冷却、伤害和半径。集中到对应武器配置，方便调参与阅读；不必把所有东西改成 ScriptableObject。
- `EmberWorld`、`EmberWorldArt`、部分 UI 与表现脚本存在密集的一行多语句写法。提交源码时，格式清晰比继续加玩法更有帮助。
- 新武器仍涉及名册、战斗注册、构筑专属/质变与文案等多个明确位置。文档应列出新增步骤及其理由，避免宣传成「只新增一个类即可」。
- 清理不可达的 Pulse、保留兼容字段等旧代码前，先确认调用与需求边界；优先加明确注释或从提交阅读路径排除，避免临近提交大范围清理造成回归。

## 工程与源码如何交付

至少提供可重新导入的 Unity 工程：

```text
EmberlightWandere/
  Assets/                 # 脚本、Editor、测试、场景、资源，以及所有相应 .meta
  Packages/               # manifest.json 与 packages-lock.json
  ProjectSettings/        # 包括 ProjectVersion.txt、输入与 Build Settings
  Docs/                   # 需求、技术分析、实现与验证说明
  Tools/                  # 经说明且可复现的辅助检查
  README.md               # 阅卷入口，当前待补
  .gitignore
  .gitattributes
```

源码已经位于 `Assets/Scripts` 和 `Assets/Editor`，完整工程应包含它们。除非对方另有明确格式要求，不必再复制一份 C# 形成第二份维护来源。**只交 APK、EXE、脚本压缩包或 unitypackage 都不能替代完整工程。** 可运行构建、录屏、截图是方便评审的附件；题面没有要求构建产物，不能把缺少 APK 单独视为题目不符合。

提交压缩包排除 `Library / Temp / Obj / Logs / UserSettings / .git / .vscode`、自动生成的 `.csproj / .sln` 与 `*_DoNotShip` 调试输出。工程必须保留资源 `.meta`，否则 GUID、引用和导入设置会丢失；见[Unity 资源元数据说明](https://docs.unity3d.com/2022.3/Documentation/Manual/AssetMetadata.html)。
