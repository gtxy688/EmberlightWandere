明天面试：一页纸

你不需要今晚学会新东西。你需要把已经懂的东西，练到能张嘴就说出来。 这一页按「今晚做什么」的顺序排，从上往下走完就行。

优先级：① 确认 Unity 里没坏（5 分钟）→ ② 把「两分钟自述」说到不用看稿 → ③ 把「那个 Bug 的故事」讲到能被打断还能接上 → ④ 让我给你模拟面试。

「整个场景只挂了一个脚本，其余全部运行时由代码创建」——一句话说明你和教程项目的差别。

「577 个 if 里只有 51 个有 else」——有人质疑你代码乱，这个数字直接反杀：那是守卫子句，不是分支地狱。

2两分钟自述（背到不用看稿）

「我做的是一个竖屏 2D Roguelike 生存射击游戏，叫《烬灯行者》，Unity 2022.3，目标平台 Android，已经出了 0.1.0 的 APK。

项目大约 6,600 行 C#、46 个文件。核心玩法是自动攻击 + 波次推进 + 清波选卡构筑，一局 25 波或 50 波。

架构上最有特点的一点：整个场景只挂了一个脚本，UI、主角、敌人、子弹全部是运行时由代码创建、由一个中心 Update 驱动。这是它的风格，也是它的代价——战斗模块不得不去问「玩家现在是在菜单里还是在游戏里」，于是战斗层里出现了 8 道 State != Playing 的判断。这是我最近在改的地方。

开发里我踩过一个印象很深的坑：加完 Boss 预警横幅之后，波次计数器开始失控、所有 Boss 都被跳过。根因是一个状态位承担了两种含义——字段名叫 bossSpawned（Boss 已生成），代码实际需要它表示「这一波是 Boss 波」。它不报错、不崩溃、编译全绿，只是某个分支永远走不到，所以定位它花了 5 个提交。

我最近在做的事就是拆这个上帝类：把 134 行文案数据抽成 EmberCopy，把开局菜单流程抽成 EmberMenuFlow，EmberGame 从 603 行降到 397 行。下一步是把 Mode 拆成「界面态」和「单局态」两个枚举。」
练习方法（别只是读）

录音说一遍 → 回放 → 改三遍。说的时候不许看稿。目标是 1 分 40 秒到 2 分 10 秒之间。

面试官几乎一定会在这段里插话。所以每一段都要能独立成答——他打断在「8 道判断」那里，你就直接展开那段；打断在 Bug 那里，就直接讲 Bug。

3「这代码是你自己写的吗？」——诚实且有利的讲法

这是你最可能被问到、也最容易被问倒的一题。先想清楚，别临场编。

先说风险：声称自己写的，一定会被戳穿

面试官只要问一句「EmberCombat 为什么不继承 MonoBehaviour？」或者「对象池的 key 是怎么设计的？」，编的人立刻露馅。这类追问没有上限。

推荐讲法：说清分工，然后把重点放在「我现在理解到什么程度」

「这个项目我是用 AI 辅助写的——需求、玩法设计、数值和验收是我定的，具体代码主要由 AI 生成。

但我不想让这个停在『我有一份自己看不懂的代码』。所以我最近做了一件事：把这份代码完整读了一遍并开始重构。我现在能说清它每一帧是怎么跑的、模块边界在哪、以及哪些地方是我会改的。

比如我知道它的风格是中心化驱动——一个 Update 推着所有子系统走；我也知道这个选择的代价，是战斗层被迫理解 UI 状态。这些是我读出来的，不是背的。」

为什么这么讲反而加分：面试官真正想验证的是「你能不能看懂并改动一份不是你写的代码」——这在真实工作里是每天都要做的事。而你今晚做的一切，正好就是这个能力本身。不要把它说成弱点，它就是你的答案。

如果面试官继续追「那你怎么保证质量？」

诚实答：「目前没有自动化测试，这是我这份项目最大的缺口。」然后给方案：「com.unity.test-framework 已经在包依赖里，但项目里 0 个 .asmdef，所以测试程序集引用不到运行时代码。我会先给 LevelConfig 和 RunProgress 建 Runtime + EditMode.Tests 两个 asmdef——这两个模块不依赖场景和帧推进，收益最高、风险最低。」

这段话是可信的，因为它是你自己项目文档里写的结论，而且技术路径正确。

4那个 Bug 的故事（你最强的一张牌）

「讲一个你遇到过最难的问题」——用这个答。它有完整的因果链、有量化、有反省。

  1. 现象。加完「Boss 预警横幅」之后，波次计数器开始失控，所有 Boss 都被跳过。
  2. 难点。不崩溃、不报错、编译全绿。Console 干净，只是行为错了。
  3. 过程（5 个提交）。

    先加战斗状态转储工具去诊断 → 发现诊断工具自己的快捷键有 bug，先修工具 → 顺着 StartWave 的调用者追，发现波次计数器在自己乱跑 → 定位到根因。

  4. 根因。bossSpawned 这个字段名说「Boss 已经生成」，但代码实际需要它表示「这一波是 Boss 波」。预警的 3 秒里 Boss 还没生成，名字说 false、逻辑却要求 true，于是清波判定把空场读成「已清完」，推进波次并级联到后面每一波。
  5. 修法与教训。明确它的唯一含义。教训是一句话：字段名必须能完整说出它唯一的那一种含义，说不出来就拆成两个。
再加一句，把故事变成洞察

「这件事让我意识到一个状态位承担两种含义，比代码写得丑危险得多——丑只是难读，双含义是让两处逻辑各自得出错误结论，而且没有任何线索指向那个布尔值。」

5高频追问 · 照这个答

他问你答
怎么保证手机帧率？ targetFrameRate = 60 + 关 VSync；对象池避免 Instantiate/Destroy 抖动；粒子硬上限 120；关键路径打了 ProfilerMarker（刷怪、选卡、池的创建与复用）
对象池怎么实现的？ EmberPool：按短字符串 key 存 Stack<GameObject>，maxPerKey 上限，池满就真销毁。诚实补充：粒子是另一套池（EmberEffects 内部的 Stack<Particle>），统一它是我要做的
状态机怎么做的？ 手写的扁平 enum（11 态）+ 早退门。主动承认：转移散落在 10 个方法、11 处赋值，没有任何地方能读出合法转移——这是我下一步要集中的
有测试吗？ 没有。这是我最大的缺口。说清原因（0 个 asmdef，测试程序集引用不到运行时代码）和补法（先给 LevelConfig / RunProgress 建）
为什么不用 ECS / DOTS？ 规模不值得。6,600 行、敌人上限几十，中心化 Tick 的开销远低于引入 ECS 的复杂度和学习成本
如果重做，你会怎么改？ ① 先把界面流程从玩法循环里拆出去（让战斗层只知道「开始跑 / 被停住」）② 再把状态转移集中到一处 ③ 最后才谈要不要上状态机框架。顺序很重要——先上框架是治标

6危险区 · 这四句千万别说

别说为什么改成
「表现层解耦了」 方向是反的：EmberKeeperAnimation 用 FindObjectOfType<EmberGame>() 反查，EmberEffects 读 game.State 「武器和进度层解耦得不错；表现层目前是反向依赖游戏层的，这是我列在待改清单里的」
「对象池统一管理敌人、投射物和特效」 有两套独立实现，「统一」是假的，一追就露 「敌人和投射物走 EmberPool；粒子的池在 EmberEffects 内部，两套还没合并」
「有一套完整的测试」 项目里 0 个测试、0 个 asmdef 「没有自动化测试，这是最大的缺口，我的补法是……」
「我用了 HFSM，比这个高级」 只在被问到状态机时才提；当成优越性讲会显得只会套框架 「另一个项目我用过层次状态机，它真正解决的是转移集中化——共享转移声明一次就处处生效。但这个项目 EmberBoss 只有 6 个状态，套框架是过度设计」
最后这条是加分项，不是地雷

能说清「什么时候不该用某个架构」，比会用更有说服力。绝大多数候选人只会说「我用了 XX 所以更好」。

7今晚的收尾动作

  1. 确认 Unity 没坏（如果你保留了我的重构）。坏了一条命令回退，别带着风险睡觉。
  2. 两分钟自述录三遍，最后一遍不看稿。
  3. Bug 故事讲两遍，第二遍故意让人打断你。
  4. 让我给你做一次模拟面试——我出题、你回答、我指出哪里含糊。这是今晚最高效的一步，因为它是唯一能暴露「你以为你懂」的环节。
现在就找我模拟面试

说一句「开始模拟面试」就行。我会按真实节奏来：先让你做两分钟自述，然后追问，最后逐条给你反馈。

或者你只想过其中一题，直接说题号也行。
