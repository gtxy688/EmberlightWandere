参考 · Reference 001

术语表

这套课从头到尾只用这里的词。任何一个词在某一课里出现了、你却不记得它指什么，回到这一页。 每个词都写了「在这个项目里具体指哪个东西」——因为同一个架构词，在不同项目里说的往往不是一回事。

怎么用这一页

不要通读背下来。当你读课或读代码卡住时再来查。查过三次的词，你自然就记住了。

一 · 课程自己的词

心跳 heartbeat
引擎每帧必然调用一次、而玩法只在它里面推进的那唯一一个方法。全项目只有一个。 本项目：EmberGame.Update()（EmberGame.cs:358）
门 · 早退门 early-return gate
形如 if (State != Mode.Playing) return; 的守卫语句。本项目不靠一个大 switch 管状态，而是靠「每个可能改状态的调用点后面补一道门」。 在 EmberCombat.Tick() 里出现 6 次以上
一条链 the chain / trace
从一个入口出发、沿真实调用顺序走到底的一条路径。例：Update → Tick → weapon.Tick → DealDamage → ApplyDamageFrom。能在脑子里走完一条链，就是看懂了这个系统的一部分。
拼全局 build the whole picture
读陌生代码的三步法：①列入口（谁被引擎叫醒）→ ②追一条链（谁调用谁）→ ③标边界（哪条线不许跨）。本课程要给你的核心能力。

二 · 架构词

模块 module
一组职责内聚、边界明确的代码。本项目在文档里切成 M1–M9，但程序集层面没有任何 .asmdef，所以边界只靠纪律维持，编译器不会替你拦。 见 Docs/architecture/00-overview.md 模块清单
契约 contract
两个模块之间唯一被允许的交互面。契约越窄，模块越能独立改动。 本项目最干净的契约：EmberWeapon.Tick(float dt, EmberWeaponContext ctx)
边界违规 boundary violation
绕过契约直接摸对方的内部。它不会立刻报错，只会让「改 A 崩 B」变得无法预测。
上帝类 god class
一个类同时承担了好几个模块的职责，于是谁改它都可能踩到别人。 本项目：EmberGame——11 态状态机 + 36 项文案表 + 开局流程 + 血量 + HUD 驱动
服务定位器 service locator
不把依赖传进来，而是自己去全局查找。它把依赖藏起来了——你读构造签名时看不到它需要什么。 本项目：EmberKeeperAnimation 里的 FindObjectOfType<EmberGame>()
反向依赖 reverse dependency
底下的层反过来依赖上面的层。方向一乱，依赖图就不再是树，改动影响无法推导。 本项目：表现层 M7 读 EmberGame.State 作播放门控
上下文对象 context object
把一堆服务打包成一个对象递给下层，代替让它直接认识宿主。契约因此变得很窄，也容易伪造。 本项目：EmberWeaponContext——M3 递给 M4 的服务包
委托注入 delegate injection
把函数当参数传下去，让下层能回调上层，却完全不需要认识上层的类。这是本项目维持「武器不认识 EmberGame」的手法。 本项目：weaponCtx.Damage = Damage;、weaponCtx.StillPlaying = () => game.State == Mode.Playing;
状态机 state machine
用一个枚举表示「现在处于哪个阶段」，所有行为都先问这个问题。 本项目：EmberGame.Mode，11 个状态
对象池 object pool
反复复用 GameObject，而不是反复 Destroy / Instantiate。手机上百毫秒一次的分配就是掉帧来源。 本项目：EmberPool（弹体、敌人视图）
Tick
「推进一小步」的约定方法名，参数通常是 float dt（本帧时长）。所有武器统一实现它，战斗层才能一视同仁地遍历。 本项目：abstract void EmberWeapon.Tick(float dt, EmberWeaponContext ctx)
组件自治 component autonomy
Unity 教程里最常见的风格：每个物体身上挂一个脚本，自己管自己的移动与行为，引擎每帧分别叫醒它们。这个项目几乎不用这种风格。
中心化驱动 centralized driving
物体本身是被动的，身上不带行为脚本；由一个中心驱动者每帧遍历它们、推着它们走。这是本项目的统一风格——所以全场景只挂了 1 个脚本，而相机、主角、敌人、子弹全都是「被别人动」的。 本项目的中心驱动者：EmberGame.Update() → EmberCombat.Tick()
层次状态机 HFSM · Hierarchical FSM
状态可以嵌套的状态机：父状态统一声明对所有子状态都成立的转移（如「任意状态 → 眩晕 / 死亡」），不必在每个子状态里重复。本项目没有用它，代价是共享转移必须逐处手写。 对比见 参考 002 · 架构体检
手写状态机 hand-rolled FSM
用 enum + 分支自己实现状态机，不引入框架。转移集中、状态少时很划算，本项目的 EmberBoss.AttackState（6 态）就是这种，写得干净。状态一多、出现共享转移，成本就会转向「转移散落各处」。
策略模式 strategy pattern
把「一类行为」抽成接口，每种行为一个实现类，运行时换实现。它是状态机的替代方案，不是同一回事：状态机关心「怎么在状态间转移」，策略关心「换一套做法」。 本项目：IEnemyBehavior + Chase/Shooter/Split/Shield/Bomber
守卫子句 guard clause
方法开头用 if (不满足) return; 提前退出，避免把主体包在层层嵌套里。它不属于「if-else 分支」——没有 else 分支就不是分支。 本项目 577 个 if 里只有 51 个有 else

三 · 这个项目里的名字

M1 – M9
文档切出的九个模块。M1 配置 · M2 单局进度与构筑 · M3 战斗与波次 · M4 武器 · M5 敌人 · M6 界面与流程 · M7 美术与表现 · M8 音频 · M9 构建与平台。 唯一权威清单在 Docs/architecture/00-overview.md
EmberGame
全场唯一的 MonoBehaviour 宿主，兼「导演」。开局四步、状态、血量、选卡、结算、HUD 刷新都在这里。读任何功能几乎都会撞到它——这既是它的作用，也是它的病。
EmberCombat
战斗模拟：刷怪、遭遇、伤害结算、死亡分裂、清波判定、Boss 招式。注意它不是 MonoBehaviour——由 EmberGame 每帧手动 Tick。
RunProgress
单局进度与构筑：拥有哪些武器、通用属性、选卡池生成、品质 roll、刷新次数、结算分。它零 UnityEngine 引用，是纯 C#，也是全项目唯一能脱离 Unity 做单测的对象。
EmberWeaponContext
M3 递给 M4 的服务包。因为有了它，武器既不需要、也不允许认识 EmberGame。这是这个仓库里最干净的一条边界。
LevelConfig
所有可调数值的家：难度倍率、波次配额、刷怪间隔、Boss 血量公式、敌人上限。改数值先来这里，不要改战斗逻辑。
Mode
EmberGame.Mode。11 个状态：Loading、Menu、SelectLength、SelectDifficulty、SelectSlots、SelectRoster、Playing、Upgrade、Paused、Lost、Won。
槽位 N · 选卡
开局流程：先选局长征程，再选难度，再选槽位 N，最后单选 1 把起始武器。禁止开局一次填满 N 槽——这是硬约束，不是待优化项。

四 · Unity 基础词（只列本课程会用的）

生命周期函数 lifecycle function
Unity 按固定顺序去调用的、名字固定的那几个方法（Awake、Start、Update…）。Unity 项目没有 main()，这些就是入口。 全项目只有 11 个，分布在 10 个 MonoBehaviour 上，见第一课
MonoBehaviour
唯一能被挂到 GameObject 上、从而被引擎调用的基类。只有继承它，才可能有生命周期函数。纯 C# 类（如 EmberCombat）必须由别人手动调用。
Update · LateUpdate
两者都是每帧一次，但 LateUpdate 在所有 Update 之后。所以「跟着别人跑完之后再对齐」的事放 LateUpdate——本项目的角色骨架就用它。 EmberKeeperAnimation.LateUpdate()
dt delta time
本帧经历了多少秒。所有「随时间变化」的量都必须乘它，否则帧率一变，游戏速度就跟着变。
