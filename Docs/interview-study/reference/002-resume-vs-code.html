架构体检：简历条目 vs 代码事实

你的判断是「项目并没有解耦，所有逻辑都耦合在一起，还用了一大堆 if-else」。 我把每一条都拿去代码里量了。结论：你的不适感是对的，但归因错了两个地方——而错的这两处， 恰好是面试官最容易追下去的地方。

一句话结论：这不是「没架构」，是「状态机是手写的，而且转移没有单一出口」。 另外，if 确实多，但它们不是 if-else 分支——577 个 if 里只有 51 个配了 else。

1先看硬数据

6,519行 C#（46 个文件）
577个 if
51个 else（含 else if）
20个 switch
30处 State 比较
最关键的一个数字

577 个 if，只有 51 个有 else——91% 的 if 是「单边」的。

这是守卫子句（guard clause）的特征，不是「if-else 分支地狱」的特征。分支地狱长这样：if…else if…else if…else… 层层嵌套，一个方法里五六条并列的互斥路径。

守卫子句长这样：if (clip == null) return; —— 提前退出，让主体保持平铺。

最密集的 EmberAudio.cs（每百行 18.4 个 if、只有 2 个 else）就是典型：它在做缺资源静默降级——音频 clip 找不到就跳过、只警告一次、不崩。那不是逻辑分支，那是防御。

所以「一大堆 if-else」这个描述，数字上不成立。真正的问题是另一个（见第 4 节）。

2这个项目其实有三种状态/行为组织方式

你说另一个项目用了 HFSM。那先确认一件事：这个项目也有状态机，而且不止一个。它只是没引入框架。

机制位置状态数转移写在哪谁保证「只有当前状态运行」
EmberGame.ModeEmberGame.cs:9 11（扁平） 散落在 10 个方法、11 处赋值 手写早退门
EmberBoss.AttackStateEmberBoss.cs:8 6（扁平） 集中在 Tick 的一条 if-else-if 链里 同一条链天然保证

值得为 EmberBoss 说句公道话

它是教科书式的扁平状态机：显式 enum、6 个状态、转移全部集中在一个 Tick 的 if-else-if 链里，一眼能读完。整个文件 78 行，还包含了所有预警圈和皇冠的美术构建。

给这 6 个状态套一层 HFSM 框架，是过度设计。这里手写是对的。

敌人行为用策略而不是状态机，也是对的

ShooterBehavior 内部确实有「接近 → 蓄力 → 开火」三阶段。但它用一个 charge 浮点数表示，没有硬套状态机——三阶段的内部时序，用一个计时器比建三个状态类更划算。

该用状态机的地方用，不该用的地方不用，这是判断力，不是偷懒。

3与 HFSM 的诚实对比

HFSM（你另一个项目）

  • 状态是对象/类，可以嵌套
  • 转移通常显式声明，能当表读
  • 父状态统一声明对全部子状态生效的转移（任意状态 → 眩晕 / 死亡），一处声明处处生效
  • 「只有当前状态运行」由框架保证
  • 新增状态 = 加一个状态类
  • 状态可单独实例化测试
  • 代价：抽象层、对象分配、调用栈变深

本项目（手写）

  • 状态是 enum 值，扁平
  • 转移散落在赋值处：11 处赋值分布在 10 个方法
  • 共享转移必须逐处手写——这正是那 30 处 State 检查和 8 道门的由来
  • 「只有当前状态运行」靠人手补门
  • 新增状态 = 加 enum 值 + 满仓库找门
  • 状态无法单独测试（必须先造出整个 EmberGame）
  • 收益：零抽象开销、一个调用栈、断点打在哪都看得见
HFSM 真正能解决的那一条

不是「把 if 换成多态」，而是转移集中化。

本项目最大的结构问题是：没有任何一个地方能让你读出「运行时合法的状态转移有哪些」。 想看全貌，你得把 EmberGame.cs 六百行的 11 处 State = … 找齐，再理解每处的触发条件。 HFSM 的转移表会把这个答案变成一张可读的表。

这才是你该在面试里讲的那句话。它比「全都解耦了」强十倍——因为它证明你能定位问题，而不是只会给结论。

5简历逐条对账

条目一 · 战斗系统架构

「将单局流程、战斗逻辑、武器系统与表现层解耦，抽象统一武器接口及战斗上下文，完成 6 种差异化武器，支持独立攻击逻辑、伤害结算及可扩展强化效果，降低新增武器的功能耦合。」
子主张判定证据
抽象统一武器接口成立abstract class EmberWeapon { abstract void Tick(float dt, EmberWeaponContext ctx); }
统一战斗上下文成立EmberWeaponContext；武器零 EmberGame 引用
降低新增武器耦合成立新增武器 = 继承 EmberWeapon + 在 EmberCombat 构造函数注册一行
武器系统解耦成立仓库里最干净的一条边界，当之无愧
战斗逻辑解耦半真EmberCombat ⇄ EmberGame 双向，22 个调用点。是环，不是单向依赖
单局流程解耦不成立单局流程就是 EmberGame 本身
表现层解耦反了表现层反向依赖游戏层，两处：EmberKeeperAnimation 反查 + 读 State；EmberEffects 读 State
这条是最大风险

「解耦」三个字下面挂着 4 项，其中 2 项为真、1 项半真、2 项不成立——而且不成立的那两项方向正好相反（表现层不是被解耦，它是反向依赖）。

懂行的面试官只要问一句「表现层怎么拿到游戏状态的？」，就会碰到 FindObjectOfType。

6面试怎么讲

不要试图辩解「其实解耦了」。改成一个有判断力的版本：

推荐说法

「这个项目的架构是一个中心驱动者 + 手写状态机。底部三层是干净的：武器只通过 EmberWeaponContext 拿服务，全程不认识 EmberGame；敌人行为是策略模式；RunProgress 零 UnityEngine 依赖，是唯一可以脱离 Unity 单测的部分。

债在上面：EmberGame 把界面流程和玩法循环装进了同一个状态机——前 6 个 Mode 是菜单，后 5 个是游戏。代价很具体：EmberCombat 里那 8 道 State != Playing 门，存在的唯一原因就是战斗层不得不去问「玩家现在是在菜单里还是在游戏里」。

所以我会先把界面流程从玩法循环里拆出去（让战斗层只知道「开始跑 / 被停住」，不需要认识 Upgrade / Paused / Menu），然后把局长的状态转移集中到一处——现在 11 处 State 赋值散在 10 个方法里，没有任何地方能读出合法的状态转移。这两步做完，再谈要不要引入显式状态机。」

三个别踩的坑

① 别说「全都解耦了」。一问表现层就穿帮。

② 别说「没有 if-else 地狱」然后就完了——要说清 577 个 if 里 91% 是守卫子句，这个数字是你的证据。

③ 别把 HFSM 当成「更高级所以更好」。要能说出它解决了哪一条（转移集中化）、以及为什么 EmberBoss 那 6 个状态不值得上框架。能说清「什么时候不该用」，比会用更有说服力。
