EmberlightWandere 架构课 · 第 2 课

一个心跳，三道门

上一课你确认了：整个项目在场景里只挂了一个脚本——EmberGame。 那这一课的问题就很自然了：它凭什么能驱动六千六百行、四十六个文件？ 答案是它每帧只做一件事，而那一件事牵出了整条链。

本课唯一目标：能画出 EmberGame.Update() 这条调用链，并解释链上每一道 if (…) return; 为什么必须存在。
第 3 节（三道门）是本课最难的一段。如果读着吃力，先把第 1、2 节和动手练习做完，那一节留到下次也行。
先结上一课的账 · 你答错了，而且错得很有价值

上一课留的问题是：Main Camera 上没挂任何脚本，镜头为什么还跟着主角跑？
你答的是「Unity 自己给 Camera 挂了个组件」。不是。

真相是：相机上一个脚本都没有。它是被别人推着走的——

// EmberGame.cs:192 —— Start() 里先拿到相机的引用
cam = Camera.main;

// EmberGame.cs:440 —— 然后每帧直接改它的位置
void UpdateCamera()
{
    cam.transform.position = new Vector3(player.position.x, player.position.y, -10);
}

没有任何东西在「驱动相机」。是 EmberGame 每帧伸手过去，把相机的位置设成主角的位置。

这个错误值得记住，因为它指向了这个项目最核心的一件事

把两件事分开：「会不会自己动」 和 「会不会动」。它们是两回事。

东西自己身上有会跑的脚本吗那它是怎么动的
Main Camera没有EmberGame 每帧直接改它的位置
主角 Keeper有一个，但只做外观EmberGame.Update() 改它的位置；那个脚本只是读取位移来做摆动
敌人有一个，但没有生命周期函数EmberCombat.Tick() 遍历它们，逐个调用行为类
火球 · 暗弹没有武器 Tick 里手动推进坐标（而武器是被 EmberCombat 调的）
本课真正要给你的东西

这个项目几乎没有「自治的组件」。所有会动的东西都是被动的，由一个中心驱动者每帧推着走。这与 Unity 教程里「每个物体挂个脚本自己管自己」的风格正好相反。

那个中心驱动者就是 EmberGame.Update()。看懂它 = 看懂整个游戏的运转方式——这就是本课要做的事。

1先破除一个错觉：这个项目没有 main()

大部分语言的程序都有一个明确的起点——main()。你顺着它往下读，就能读完整个程序。Unity 不是这样： 引擎自己写好了 main()，它每帧做的事情是去你的脚本里找几个名字固定的方法，然后调用它们。这些方法叫生命周期函数。

上一课你只看到 1 个脚本被挂上去。但那 1 个脚本里，有哪些方法会被引擎主动叫到？下面这个漏斗把 46 个文件一路收敛到 1 个方法：

层级数量含义
.cs 文件4640 个运行时 + 6 个编辑器脚本
继承 MonoBehaviour 的类10只有它们能被挂到 GameObject 上、被引擎叫醒
Unity 生命周期函数11真正会被引擎主动调用的方法
其中每帧都跑的5Update ×4 + LateUpdate ×1
其中推进玩法的1EmberGame.Update()

那 11 个分别是谁，在干什么：

生命周期函数位置职责模块
Awake()EmberAudio.cs:99音频总线自举M8
Start()EmberGame.cs:182全场唯一的总装线M6
Update()EmberGame.cs:358全场唯一的玩法心跳M3 驱动
OnApplicationPause()EmberGame.cs:547切到后台就自动暂停M6
OnApplicationFocus()EmberGame.cs:548失去焦点就自动暂停M6
OnDestroy()EmberGame.cs:214退出时把 timeScale 复位M6
Update()EmberIntro.cs:149加载页进度M7
Update()EmberEffects.cs:33粒子存活M7
LateUpdate()EmberKeeperAnimation.cs:44主角骨架摆动M7
Update()EmberCardMotion.cs:12卡牌飞入动画M6
OnDisable()EmberCardMotion.cs:11卡牌被关掉时停协程M6
第一个洞察

剩下 36 个文件根本不会被引擎当生命周期叫醒。它们是纯 C# 类，必须有人手动 new 出来再调用。EmberCombat 就是这样——它连 MonoBehaviour 都不是，全靠 EmberGame 每帧手动 Tick。

所以「看懂这个项目」从来不需要读完 46 个文件。你需要的是找到这 11 个入口，然后顺着往下走。

两处容易漏掉的入口

一、另有 4 个 MonoBehaviour（EmberEnemySilhouette、EmberGodsSelectPanel、EmberUpgradePanel、EmberSettingsPanel）一个生命周期函数都没有——它们只是被当作「能挂在物体上的容器」在用。可见继承 MonoBehaviour 不等于会被引擎驱动。

二、EmberCardMotion 还实现了 IPointerDownHandler 等接口，Unity 是通过接口方法（OnPointerDown）回调它的。这不算生命周期函数，但同样是引擎驱动的路径。查入口时别只顾着搜 Update。

2第二层：那条链

Start() 是总装线——它 new 出 EmberCombat、EmberMenuUi，建好 Run world 和 Keeper，把 EmberEffects 交给战斗。 跑完 Start()，线就接好了。之后每一帧，只有 一件事在推进玩法： 

EmberGame.Update()  · 全场唯一的玩法心跳
│
├─ 检查安全区有没有变
├─ if (State != Playing) return;          · 门 ①
├─ Elapsed += dt;   hurtTimer -= dt;
├─ ReadInput()                             · 按 Esc 会 Pause()，State 变了
├─ if (State != Playing) return;          · 门 ②
├─ 移动主角 → EmberWorld.Clamp → UpdateCamera
│
├─ combat.Tick(dt)                         · 战斗推进 · M3
│   │
│   ├─ if (game.State != Playing) return;   · 门
│   ├─ 刷怪 / Boss 预警倒计时 / 遭遇事件
│   ├─ 每个敌人：behavior.Tick(dt, enemyCtx)
│   │    └─ game.HurtPlayer(…)  · 血量归零会 EndRun(false) → State = Lost
│   ├─ 灼烧光环结算
│   ├─ 把 PlayerSpeed / Progress / Elapsed / Pool 填进 weaponCtx
│   ├─ 每把武器：weapons[w].Tick(dt, weaponCtx)   · 武器 · M4
│   │    └─ ctx.DealDamage(i, dmg, from)
│   │         └─ EmberCombat.ApplyDamageFrom() → e.hp -= amount
│   ├─ enemyProjectiles.HitPlayer(…)
│   └─ ResolveDeaths()
│        └─ game.OnWaveCleared(wave)  · 清波了
│             └─ Progress.OfferChoices() → OfferUpgrade() → State = Upgrade
│
├─ if (State != Playing) return;          · 门 ③
└─ UpdateHud()

把这张图从下往上读一遍，再从下往上读一遍。这就是整个游戏的骨架。 M1–M9 那九个模块只是贴在这条链各个节点上的标签；这条链本身才是「整体框架」。

注意最后一列

每往下走一层，就换一个模块：M6 的 Update 驱动 M3 的 Tick，M3 再驱动 M4 的 Tick，伤害最后落回 M3 的 ApplyDamageFrom。依赖是单向往下的——这就是为什么这个项目好读。

3第三层：为什么到处都是 if (…) return;

再看一眼 EmberCombat.Tick()。同一种写法出现了 六次以上： 

for (int w = 0; w < weapons.Count; w++)
{
    if (game.State != EmberGame.Mode.Playing) return;   // ← 每调一把都再问一遍
    weapons[w].Tick(dt, weaponCtx);
}

为什么要反复问？因为被你调用的东西，会中途把状态改掉：

链上的调用它可能把 State 改成
ReadInput() 里按了 EscPaused
HurtPlayer() 里血量归零Lost
ResolveDeaths() 清完一波Upgrade
Boss 被击败且是最终波Won

一旦进了 Upgrade，选卡面板已经弹出来了，后面的代码绝不能再跑——否则你会一边选卡一边挨打。 所以这个项目管理状态机的办法不是一个大 switch，而是： 每个可能改状态的调用点后面，都补一道早退门。 你在这份代码里看到的每一道 if (State != Playing) return;，都是有人曾经踩过的坑。

真实证据 · 就在你的仓库里

EmberCombat.StartWave() 里留着一段注释（EmberCombat.cs:213-218），讲的就是漏掉一道门会发生什么：

「…leaving it false through the lead-in let them read the empty Boss wave as already cleared and advance the wave: the Boss was skipped before it could spawn and the advance cascaded through every following wave.」

对应的提交是 528a40f Fix the runaway wave counter that also skipped every Boss——波次计数器一路狂飙、所有 Boss 被跳过，根因就是一道门的位置不对。

这条规则以后会反复用到

在这个项目里加新逻辑时，先问自己一句：「我这段代码，可能在哪个调用里被改状态？」 如果想不出来，就去看它前面那道门在哪。

5练习二 · 亲手把这条链看一遍（约 15 分钟）

不要只读。要亲眼看见「门」把代码挡住了——看见一次，胜过读十遍。

  1. 加第一个探针。打开 Assets/Scripts/Core/EmberGame.cs，找到 void Update()（第 358 行）， 在它花括号后的第一行插入： 
    if (Input.GetKeyDown(KeyCode.F1)) Debug.Log("Update 在跑，State = " + State);

    注意必须放在最顶上，要在门 ① 之前——这样无论什么状态它都会打印。

  2. 加第二个探针。打开 Assets/Scripts/Combat/EmberCombat.cs，找到 public void Tick(float dt)（第 244 行）， 在那道门（第 246 行）之后插入： 
    if (Input.GetKeyDown(KeyCode.F2)) Debug.Log("战斗 Tick 跑到了，波次 " + wave);

    这个放在门后面——这正是关键。

  3. 回到 Unity，等编译完，确认 Console 没有报红。
  4. Play →「点亮旅程」→ 选 25 波 → 标准 → 选槽位 → 选 1 把武器 → 进战斗。
  5. 在战斗中按 F1，再按 F2。

    Console 应该各出一行：Update 在跑，State = Playing 和 战斗 Tick 跑到了，波次 1。

  6. 关键一步。清掉一波，让选卡面板弹出来。然后：先按 F2，再按 F1。
    • F2 什么都不打印——证明 combat.Tick 被门挡住了，玩法停住了。
    • F1 打印 Update 在跑，State = Upgrade——证明 Update 还在每帧运行，只是提前 return 了。
  7. 顺手再试一次：按 Esc 暂停，重复第 6 步。结论一样。
  8. 验完删掉这两行探针，别提交上去。
你从这一步拿到的结论

Update 每帧都在跑，玩法只在 Playing 时跑。
换句话说：「游戏停了」不等于「代码停了」。——这就是为什么要门，也是为什么读这份代码必须先看 State。
