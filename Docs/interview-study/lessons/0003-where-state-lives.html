一局游戏的状态，藏在两个地方

你上一条说的是「状态转移没有单一出口」。这个判断是对的。 这一课我把代码里缺的那张图补出来给你——然后你会发现一件更麻烦的事： 这张图只画了一半，另一半的状态根本不在 Mode 里。

本课唯一目标：能说出「这个游戏的状态记在哪两个地方」，并讲清那个「所有 Boss 被跳过」的 bug 是怎么来的。
这是全课程最接近「真实工程」的一课——你会看到一个状态位重载，如何吃掉五个提交。

一、Playing 有 4 条入口路径（SetPlaying 共 5 个调用点：选完起始武器 :338、清波但不刷卡 :448、选完卡 :501、从暂停恢复 :514 / :516 两个分支）。所以「回到 Playing」不是一条路径。

二、Paused 只能从 Playing 进——因为 Pause() 第一行就是 if (State != Mode.Playing) return;。在选卡界面按 Esc 是没反应的，这不是 bug，是设计。

2第二处：EmberCombat 里那 14 个私有状态位

上面那张表只讲了一半。真正决定「这一波打到哪了」的东西，一个字都不在 Mode 里——它们在 EmberCombat 的私有字段里：

管什么字段行
波次进度wave · waveQuota · waveSpawned · waveKilled · extraSpawned:59-62, :43
Boss 节奏bossSpawned · bossWarning · bossEnemy:55, :58, :52
清波协调awaitingUpgrade:55
遭遇事件eventTriggered · encounterTimer · encounterText:40-42
计时与缓存spawnTimer · burningTimer · hasLastPlayerPos:54, :41, :35

看清楚这件事的后果——Tick 里那句「现在该不该刷怪」的判断：

if (!awaitingUpgrade && !bossSpawned && wave < config.BossWave
    && waveSpawned < waveQuota && enemies.Count < config.EnemyLimit)
这就是你上一条感受到的那件事

一个决策依赖 5 个条件，其中 2 个是隐藏状态位。而 Mode 完全不知道它们的存在——切到 Upgrade 时，awaitingUpgrade 是真是假、bossSpawned 是真是假，Mode 一概不知。

所以「游戏现在是什么状态」这个问题，没有单一答案。这就是转移集中化真正要解决的东西——不只是把 11 处赋值收拢，还要把这两处的状态合并成一个来源。

3一个位、两种含义：那个吃掉五个提交的 bug

上一条我说过「你在这份代码里看到的每一道门，都是有人曾经踩过的坑」。bossSpawned 就是最大那个坑，而且它的注释还留在代码里（EmberCombat.cs:213-218）：

「bossSpawned means "this wave is a Boss wave", not "the Boss object exists". …leaving it false through the lead-in let them read the empty Boss wave as already cleared and advance the wave: the Boss was skipped before it could spawn and the advance cascaded through every following wave.」

翻译一下：这个字段名字叫「Boss 已生成」，但它实际的含义是「这一波是 Boss 波」。这两种意思在 Boss 出现之前是相反的——名字说「还没生成」，代码却需要它说「已经是 Boss 波了」。

于是：预警的 3 秒里，波次清理逻辑看到 bossSpawned == false、场上又没敌人，判定「这波已经清完了」→ 推进波次 → Boss 还没出场就被跳过 → 而这次推进又级联到后面每一波。

这个坑是完整的，五个提交都在仓库里
  1. 5ef7d51 Restore the keeper shadow, warn before Boss waves
    ← 为了加「Boss 预警横幅」引入了 bossWarning，同时让 bossSpawned 提前置位。坑挖好了。
  2. 73ada9f Add combat state dump and pre-boss jump for diagnosing the Boss wave
    ← 发现 Boss 不对劲，先加诊断工具。
  3. be8386a Fix the boss probe hotkeys: read them from the game, not an editor hook
    ← 诊断工具自己有 bug，先修工具。
  4. 6a1a215 Trace StartWave callers: the wave counter runs away on its own
    ← 顺着调用者找到根因：波次计数器在自己乱跑。
  5. 528a40f Fix the runaway wave counter that also skipped every Boss
    ← 修复：明确 bossSpawned 从「已经生成」改义为「这一波是 Boss 波」。
这一课真正要你带走的东西

一个状态位承担两种含义，代价是四个提交的调试。

它不报错、不崩溃、编译全绿——只是某个分支永远走不到。而「某个分支永远走不到」在游戏里表现为「Boss 莫名其妙不出现」， 你没有任何线索指向那个布尔值。

以后你写状态位时，只有一条规则：字段名必须能完整说出它唯一的那一种含义。说不出来，就拆成两个。

4动手 · 亲眼确认状态在两个地方（约 10 分钟）

这次不加探针了，用更直接的方式：看 Inspector 看不了的运行时状态。

  1. 先确认第一处。打开 EmberGame.cs，看 Mode 的定义（第 9 行）。数一下确实是 11 个。
  2. 再确认第二处。打开 EmberCombat.cs，跳到第 35～62 行。这不到 30 行里全是状态字段。

    关键动作：把 bossSpawned（第 55 行）和 awaitingUpgrade 圈出来。它们和 wave（59 行）一样，都是「游戏进行到哪了」的一部分——但它们不在 Mode 里。

  3. 找到那句五条件的判断。在 Tick 里（第 250 行附近），你会看到那句 if (!awaitingUpgrade && !bossSpawned && …)。
  4. 读那段注释。EmberCombat.cs:213-218。这是全项目最有价值的一段注释——它把一个真实 bug 的根因留在了现场。
  5. 跑一次验证。Play → 进战斗 → 打到第 10 波（Boss 波）。

    你会看到「守卫试炼 · 暗影来袭」的预警横幅，3 秒后 Boss 出现。那 3 秒就是 bossWarning 的倒计时——也就是当年让波次计数器失控的那 3 秒。

  6. 看一眼提交。在项目根目录执行： 
    git log --oneline --reverse | Select-String "BOSS|Boss|boss|wave"

    你会看到上面那五个提交排在一起。这是一个真实 bug 的完整考古现场。

你从这一步拿到的结论

「游戏现在是什么状态」在这个项目里没有单一答案——它被拆在 EmberGame.Mode 和 EmberCombat 的 14 个私有字段里。

而当初那个 bug，就是从这两处状态交界的缝隙里钻出来的。

6所以，「该改什么」有答案了

你在上一条里说的「状态转移没有单一出口」，到这里可以升级成一句更准的话：

一句话诊断

这个项目的问题不是「状态机写得丑」，是「状态记在两个地方，而且其中一处的一个位还兼着两种含义」。

要修的话，第一步不是引入 HFSM 框架，而是先把 EmberCombat 那 14 个字段里的「准状态」（bossSpawned / awaitingUpgrade / eventTriggered）收进状态机。框架可以之后再谈。
